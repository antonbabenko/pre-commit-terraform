## Why

Users repeatedly ask for two related things that turn out to be the same underlying gap: (1) a wrapped tool (terraform, tflint, terraform-docs, tfsec/trivy, terrascan, infracost, tfupdate, terragrunt, opentofu) must already be installed/on `PATH` before a hook can run at all ([#270](https://github.com/antonbabenko/pre-commit-terraform/issues/270), [#722](https://github.com/antonbabenko/pre-commit-terraform/issues/722)), and (2) there is no way to pin/select a *specific* version of that tool per-hook, independent of whatever happens to be on `PATH` or baked into a Docker image build ([#188](https://github.com/antonbabenko/pre-commit-terraform/issues/188), open since 2021). The repo already owns a working "download a pinned or latest version from a GitHub release" mechanism (`tools/install/_common.sh::common::install_from_gh_release`) — it is just wired exclusively to Docker build-time (`ARG *_VERSION`), never to hook run-time, and never controllable per-repo.

## What Changes

- New opt-in hook-config key, `--hook-config=--tool-version=X.Y.Z`, usable on any hook that wraps a GitHub-release-distributed binary, including Terraform/OpenTofu (via `common::get_tf_binary_path`). Mirrors the existing dash-style, hook-agnostic naming convention already used for `--tf-path` and `--parallelism-limit`.
  - Every hook resolves its own binary path itself, in its own `main()` (via the new resolver for most tools, or via `common::get_tf_binary_path` for the three Terraform-consuming hooks), and passes it into `common::per_dir_hook` as an explicit `tool_path` parameter, threaded through to `per_dir_hook_unique_part`/`run_hook_on_whole_repo`. Because `common::get_tf_binary_path` is therefore only ever called by the three hooks that actually consume its result (`terraform_validate`, `terraform_fmt`, `terraform_providers_lock`), a different hook's own unrelated `--tool-version` (set for its own tool) can never be misread as a Terraform pin — there's no shared, unconditional call site left for that to happen at. Confirmed no hook needs to pin both Terraform *and* a second tool simultaneously, so a single shared key is safe.
- New shared resolver in `hooks/_common.sh` that, only when a version is explicitly requested:
  1. Checks a tfenv-style cache directory (`<cache_root>/<tool>/<version>/<tool>`, cache root controlled by a new `PCT_TOOL_CACHE_DIR` env var — if set, used as the complete cache-root path as-is; if unset, defaults to `$XDG_CACHE_HOME/pre-commit-terraform` when `XDG_CACHE_HOME` is set, otherwise `$HOME/.cache/pre-commit-terraform` — e.g. `$HOME/.cache/pre-commit-terraform/tflint/0.50.0/tflint`) for an already-downloaded binary of that exact version.
  2. On a cache miss, downloads it by **invoking the existing `tools/install/<tool>.sh` installer script directly, as a subprocess** — exporting that tool's expected version env var (the same `${TOOL^^}_VERSION` name the script already derives from its own filename, e.g. `TFLINT_VERSION`), computing and exporting `TARGETOS`/`TARGETARCH` via `uname` (these are Docker-buildx-provided automatic args at build time; outside a Docker build they don't exist and must be derived at run-time via `uname` — `uname -s` lowercased for OS, `uname -m` mapped `x86_64→amd64` / `aarch64|arm64→arm64` for architecture), and running the script with its working directory redirected (in a subshell) to the target cache path — since the installer already just downloads-and-extracts into `cwd`, redirecting `cwd` to the cache directory *is* the caching step. This reuses the existing, already-tested per-tool download logic with zero duplicated constants, and requires exactly one small, backward-compatible change: `tools/install/_common.sh`'s unconditional `source /.env` (only present inside the Docker `builder` stage) becomes conditional (`[[ -f /.env ]] && source /.env`) so the same script also runs correctly at hook run-time, where the version is already exported by the caller instead. Docker build behavior is unaffected.
  3. Resolves to an **absolute path**, never mutates `PATH`.
- If a requested `--tool-version` differs from whatever would otherwise be found via existing `PATH`/precedence lookup, the resolver **warns, then proceeds with the pinned/cached version** — pinning always wins once requested; the warning exists purely for visibility.
- A new `--hook-config=--tool-version-mode=strict|prefer-local` toggle controls that precedence: `strict` (default, matches the behavior above - pin always wins) or `prefer-local` (if the tool already resolves via plain `PATH` lookup, use that as-is and skip the cache/download path entirely; only falls through to the pinned/cached version if nothing is found locally). Read directly by the shared resolver, so no per-hook wiring changes were needed for this addition.
- When no `--tool-version` is requested, behavior is byte-for-byte unchanged: existing `PATH`-lookup / `command -v` precedence continues to apply. Fully backward compatible, opt-in only.
- Because resolution is keyed by exact version and returns a path (not a `PATH` mutation), the same hook id can be listed multiple times in one `.pre-commit-config.yaml`, each pinned to a different `--tool-version`, to test compatibility across tool versions in a single run/CI job.
- All eligible hooks are wired to the resolver in one pass (no phased/staged rollout across tools).
- Documentation additions to `README.md`:
  - A new **"All hooks: `--tool-version`"** section (placed and formatted like the existing "All hooks: ..." sections — environment variables in `--args`, disable color output, log levels, etc.) describing usage.
  - A "mount a cache directory to persist across container runs" note, mirroring the existing `TF_PLUGIN_CACHE_DIR` Docker guidance.
  - A copy-paste Renovate `customManagers` (regex) recipe so consumers can make their own `--hook-config=--tool-version=` pins auto-bumpable, using the same `# renovate: datasource=... depName=...` annotation convention already established for Dockerfile `ARG *_VERSION` pins. This is a documentation-only deliverable — neither Renovate's built-in `pre-commit` manager nor its `dockerfileVersions` preset can see inside `args:`/hook-config strings, so nothing in this repo needs to change for it to work.

**Explicitly out of scope for this change:**
- pre-commit.ci support. Its run stage executes with networking disconnected, so no download-on-demand mechanism can work there regardless of implementation language; revisit only if/when hooks move to a `language: python` implementation (tracked separately in [#648](https://github.com/antonbabenko/pre-commit-terraform/issues/648)), which gets a provisioning phase with network access.
- Tools without a direct GitHub-release binary story: `checkov` (pip-installed) keeps its existing install path untouched.
- Runtime fetching of tflint plugins / terrascan policies (separate, `--init`-style network dependency already present today, unrelated to which *binary* version is used).
- Any change to how tools are installed at Docker build time; the existing `tools/install/*.sh` build-time flow is untouched (aside from the one conditional-sourcing tweak noted above, which is a no-op during a Docker build).
- Checksum/signature verification of downloaded binaries (parity with the existing build-time mechanism, not a regression).

## Capabilities

### New Capabilities
- `hook-config-tool-version`: opt-in, per-hook, cached, on-demand resolution of a specific version of a wrapped tool's binary via `--hook-config=--tool-version=X.Y.Z`, for hooks that invoke a GitHub-release-distributed CLI tool.

### Modified Capabilities
(none — no existing specs in `openspec/specs/` to modify; this change is additive)

## Impact

- `hooks/_common.sh`: add the shared version-resolution function(s) — cache lookup, OS/ARCH detection, subprocess invocation of the matching `tools/install/<tool>.sh`, warn-and-proceed-on-mismatch logic. Also: `common::per_dir_hook` gains an explicit `tool_path` parameter (threaded to `per_dir_hook_unique_part`/`run_hook_on_whole_repo`) and no longer resolves anything Terraform-specific internally — every caller resolves its own `tool_path` first.
- `tools/install/_common.sh`: one-line change making `source /.env` conditional on the file's existence. No other changes; Docker build behavior is unaffected.
- All binary-wrapping hook scripts (`terraform_tflint.sh`, `terraform_docs.sh`, `terraform_trivy.sh`, `terraform_tfsec.sh`, `terrascan.sh`, `tfupdate.sh`, `terragrunt_*.sh`, `infracost_breakdown.sh`, and the `terraform`/`opentofu` path via `common::get_tf_binary_path`): wired to the new resolver in one pass, all reading the same `--tool-version` key, ahead of each hook's current `command -v` / direct-invocation assumption.
- `README.md`: new "All hooks: `--tool-version`" usage section, cache-persistence note, and Renovate-recipe section.
- No `Dockerfile` / `.dockerignore` changes required (confirmed: `tools/install/*.sh` already reaches hook run-time in both bare-metal and Docker via pre-commit's own repo-clone step, the same way `lib_getopt` already does today).
