## Context

- `pre-commit-terraform` wraps ~11 external CLI tools via `language: script` (`unsupported_script`) hooks. Per pre-commit's own docs, that language "will not be given a virtual environment to work with — if it needs additional dependencies the consumer must install them manually." This is a deliberate choice (confirmed: not all wrapped tools have a uniform `go install`/`pip install` story — terraform/opentofu in particular are closed-release-distribution-only), not an oversight.
- Today, which tool version actually runs is decided by exactly one of: whatever is on `$PATH` (bare-metal), or whatever was baked in at `docker build` time via `ARG *_VERSION` (consumed by `tools/install/_common.sh::common::install_from_gh_release`, which resolves a GitHub Releases URL by regex and downloads it). This has produced five years of recurring, related issues: [#188](https://github.com/antonbabenko/pre-commit-terraform/issues/188) (2021, still open — "allow specifying terraform-docs version"), [#270](https://github.com/antonbabenko/pre-commit-terraform/issues/270) (2021, closed as user error — "tflint command not found"), [#722](https://github.com/antonbabenko/pre-commit-terraform/issues/722) (2024–2026, open and active — "automate dependencies"), [#946](https://github.com/antonbabenko/pre-commit-terraform/issues/946) (2025, resolved — GitHub API auth for the *build-time* installer).
- Maintainers/collaborators (yermulnik, MaxymVlasov — both repo COLLABORATORs, comments as recent as 2026-01-14 on [#722](https://github.com/antonbabenko/pre-commit-terraform/issues/722)) have repeatedly, thoughtfully pushed back on a generic auto-installer: the wrapped tools are heterogeneous, and there are already several competing version-manager conventions (`tenv`, `tfswitch`, `asdf`, `mise`, `aqua`) a from-scratch mechanism would seem to compete with. Their stated current position is "the consumer ensures the tool exists on `PATH`." This is not a rejection, but a standing objection any proposal needs to engage with by staying narrow.
- pre-commit.ci (confirmed via a pre-commit.ci-affiliated contributor's own comment on [#722](https://github.com/antonbabenko/pre-commit-terraform/issues/722)) runs hooks with networking disconnected during its run stage. No download-on-demand mechanism, in any implementation language, can work there — only pre-commit's native per-language provisioning (which runs before the network is cut) does.
- `tools/install/_common.sh::common::install_from_gh_release` already implements "resolve latest-or-specific-version GitHub release asset via regex against `/releases` or `/releases/latest`, download, extract" — but only ever runs once, at Docker build time. Two build-time-only details matter for reuse at run-time:
  - It reads its target version from a `${TOOL}_VERSION` environment variable, populated via an unconditional `source /.env` — a file created only inside the Docker `builder` stage (`RUN touch /.env && ...`). It does not exist outside a Docker build.
  - The per-tool release-URL regexes reference `$TARGETOS`/`$TARGETARCH`, which are Docker buildx-provided automatic build args — also not defined outside a Docker build.
  It has no caching (irrelevant when it only runs once per image build) and no checksum verification.
- `tools/install/*.sh` is already allow-listed through `.dockerignore` (`!tools/install/*.sh`) and is a git-tracked part of the repo — meaning it already arrives at hook run-time automatically, in both bare-metal and inside this project's own Docker image, via pre-commit's own git-clone-based hook installation (pre-commit always clones a hook repo's full tree at the pinned `rev:` on first use). This is the exact same mechanism that already makes `hooks/_common.sh`'s `common::initialize` function work (`. "$script_dir/../lib_getopt"`), with zero Dockerfile involvement.
- External prior art surveyed (`tfenv`, `aquasecurity/trivy`'s `install.sh`, GitHub composite-action install patterns): the one thing consistently present there but structurally unnecessary in this repo's *existing* build-time downloader is **caching keyed by version**. Without it, a runtime-triggered version of the same logic would re-download on every single `pre-commit run`.

## Goals / Non-Goals

**Goals:**
- Let a `.pre-commit-config.yaml` author pin an exact tool version per hook via `--hook-config=--tool-version=X.Y.Z`, resolved/downloaded/cached on demand, with zero effect on any hook that doesn't set it.
- Work identically for bare-metal `pre-commit` and this project's Docker image, with no `Dockerfile`/`.dockerignore` changes.
- Support declaring the same hook id multiple times in one config, each pinned to a different version, for cross-version compatibility testing — by resolving to a distinct cached absolute path per version rather than mutating a single shared `PATH` entry.
- Make the pinned-version string trivially Renovate-bumpable via a documented `customManagers` recipe (documentation only — no code in this repo needs to know about Renovate).
- Reuse the existing `tools/install/<tool>.sh` download logic as-is (by invocation), rather than re-deriving or duplicating per-tool download parameters.

**Non-Goals:**
- pre-commit.ci support. Blocked structurally by its network-disconnected run stage; would need a `language: python` provisioning-phase rewrite (tracked separately, [#648](https://github.com/antonbabenko/pre-commit-terraform/issues/648)) to even be possible. Not attempted here.
- Checksum/signature verification of downloaded binaries. The existing build-time mechanism, and the reference implementation this was modeled on, both skip it. Parity, not a regression — a plausible separate follow-up.
- Any tool without a direct release-binary distribution story (`checkov`/pip keeps its current, already-working path untouched).
- tflint-plugin / terrascan-policy network fetching (pre-existing, orthogonal `--init`-style dependency, unrelated to which tool *binary* version is selected).
- Changing how tools are installed at Docker *build* time.
- Becoming a general-purpose dependency/version manager, or replacing `tools/install/`'s build-time role.
- A phased/staged tool-by-tool rollout (see Decisions — every eligible hook is wired in one pass).

## Decisions

1. **Downloads are performed by invoking the existing `tools/install/<tool>.sh` installer script directly, as a subprocess — not by re-deriving or duplicating its parameters.**
   Rather than sourcing `tools/install/<tool>.sh`'s `GH_ORG` / `DISTRIBUTED_AS` / regex constants into `hooks/_common.sh` (which would mean maintaining two copies of the knowledge of how to build each tool's download URL), the runtime resolver instead:
   1. Computes `TARGETOS`/`TARGETARCH` via `uname` (`uname -s` lowercased for OS; `uname -m` mapped `x86_64→amd64`, `aarch64|arm64→arm64` for architecture) and exports them — these exist automatically during a Docker buildx build but not otherwise, so they must be derived at run-time.
   2. Dynamically exports the tool's expected version env var — the same `${TOOL^^}_VERSION` name (with `-`→`_`) the installer script already derives from its own filename (e.g. `tflint.sh` → `TFLINT_VERSION`) — set to the requested `--tool-version` value.
   3. In a subshell (so the working-directory change never leaks into the calling hook script), `cd`s into the target cache directory for that exact tool+version, then invokes `tools/install/<tool>.sh` as a plain subprocess — not sourced, for full variable/`set -e` isolation from the calling hook's own shell state.
   Because the installer script already just downloads-and-extracts into `cwd`, redirecting `cwd` to the cache directory *is* the caching step — no separate download-then-move logic is needed. This reuses 100% of the existing, already-tested per-tool logic with zero duplicated constants.
   This requires exactly one small, backward-compatible change: `tools/install/_common.sh`'s unconditional `source /.env` (line 12) only works inside the Docker `builder` stage, where that file is created; it becomes `[[ -f /.env ]] && source /.env` so the same script also runs correctly when invoked directly at hook run-time, where `/.env` doesn't exist and the version env var is already exported by the caller instead. Docker build behavior is unaffected, since `/.env` still exists and is sourced there exactly as before.
   *Alternatives considered*: (a) source just the per-tool constants into `hooks/_common.sh` and re-implement the download call there (an earlier draft of this decision) — rejected, it duplicates knowledge of URL-building rules across two call sites that would need to be kept in sync. (b) Duplicate the whole download function into `hooks/_common.sh` — rejected for the same reason, plus doubles the maintenance surface.

2. **Cache layout: tfenv-style nested `<cache_root>/<tool>/<version>/<tool>`**, not a flatter `<tool>-<version>` filename style. This is also literally the directory the installer subprocess's `cwd` is redirected to (see Decision 1), so the nested path doubles as both "where we look for a cache hit" and "where the subprocess drops the binary on a cache miss."
   *Alternative considered*: flat filename-suffixed cache. Simpler — not chosen, but not wrong either; revisit if nesting adds friction without payoff.

3. **Cache root is controlled by a new `PCT_TOOL_CACHE_DIR` environment variable, which — when set — redefines the complete cache-root path as-is (no further suffixing).** When unset, it defaults to `"${XDG_CACHE_HOME:-$HOME/.cache}/pre-commit-terraform"` (i.e. `$XDG_CACHE_HOME/pre-commit-terraform` if `XDG_CACHE_HOME` is set, otherwise `$HOME/.cache/pre-commit-terraform`). The `pre-commit-terraform` subdirectory is only appended by this default computation, not when `PCT_TOOL_CACHE_DIR` is explicitly set — namespacing default caches under their own subdirectory rather than depositing per-tool directories directly into a shared cache root, so they can't collide with or be mistaken for some other tool's own cache entries. Follows the existing `PCT_*` naming convention already used for `PCT_LOG` and `PCT_TFPATH`.

4. **Resolution always returns an absolute path; it never mutates `PATH`.** Mirrors `common::get_tf_binary_path`'s existing contract exactly. This is what makes "same hook, multiple pinned versions in one config" work at all — a `PATH`-mutating design could not support two invocations pinned to different versions without one clobbering the other.

5. **On a mismatch between a requested `--tool-version` and whatever existing precedence (e.g. `PATH`) would otherwise resolve, the system warns and then proceeds with the pinned/cached version.** Pinning, once requested, always wins — that is the entire point of the feature. The warning (via the existing `common::colorify "yellow" ...` convention) exists purely for visibility, e.g. "requested 1.7.5, but PATH has 1.9.0 — using 1.7.5"; it does not block execution or require confirmation.

6. **A `--hook-config=--tool-version-mode=strict|prefer-local` toggle controls the warn-and-proceed precedence from Decision 5, default `strict`.** `strict` is exactly the Decision 5 behavior (pin always wins). `prefer-local` inverts it: if the tool already resolves via plain `PATH` lookup, that local binary is used as-is and the cache/download path is skipped entirely; only falls through to resolving the pinned/cached version if nothing is found locally. Read directly by `common::resolve_tool_path` via `common::get_hook_config_value`, the same way the version keys themselves are read - no changes needed to any of the per-hook call sites or to `common::get_tf_binary_path` for this addition, since both already funnel through the one shared function.
   *Alternative considered*: pass the mode as an explicit third argument to `common::resolve_tool_path`, threaded through by every caller. Rejected - it would require touching all nine already-wired call sites again for no behavioral benefit over reading the same global `HOOK_CONFIG` the function already has access to.

7. **Every eligible hook is wired to the resolver in one pass, not phased tool-by-tool.** The resolver is a single shared function, and each hook's wiring is a small, mechanical, independent change (call the resolver, use its returned path instead of assuming `PATH`). There is no meaningful risk-reduction benefit to phasing (e.g. tflint + terraform first) that would offset the coordination overhead of multiple review passes.

8. **Every hook passes `common::per_dir_hook` a plain `tool_name` string (e.g. `"tflint"`, `"tf"` for the three Terraform-consuming hooks, or `""` for checkov); resolution to an actual `tool_path` happens in one place, inside `common::per_dir_hook` itself, via `common::resolve_tool_path`.** This replaced two earlier designs in turn: first, each hook pre-resolved its own `tool_path` in `main()` and passed the resolved path in; before that, `common::get_tf_binary_path` was called unconditionally for every hook from inside `common::per_dir_hook`, gated on `$HOOK_ID` to avoid a different hook's unrelated `--tool-version` being misread as a Terraform pin. Passing a `tool_name` instead of a pre-resolved path collapses both problems at once: `common::per_dir_hook` reads `--tool-version` and calls `common::resolve_tool_path "$tool_name" "$tool_version"` exactly once, for every hook, the same way; there is nothing left to gate, because the dispatch inside `common::resolve_tool_path` (Decision 9) keys off the tool name actually being resolved, not off which hook happens to be asking - a `tflint`-wrapping hook can never accidentally trigger Terraform-specific logic no matter what `--tool-version` string it's given, because `"tflint" != "tf"`.
   *Consequence*: `terraform_tflint.sh` is the one exception that still needs its own `tool_path` computed early in `main()` (calling `common::resolve_tool_path` directly, same as `common::per_dir_hook` does internally) - its pre-flight `tflint --init` check runs once, before and separately from `common::per_dir_hook`, so it can't rely on that internal resolution. The minor duplicate resolver call this causes is a cache hit in practice, not a second download.

9. **`common::resolve_tool_path` is one single function, the only entry point every caller uses unconditionally, and it internally decides whether/how to resolve rather than making callers pre-check `$tool`/`$version` themselves.** Concretely: given `tool=""` (checkov) it returns empty, a no-op; given `tool == "tf"` (a sentinel, not a real installable tool - see below) it delegates to `common::get_tf_binary_path "$version"` (which has its own additional precedence rungs - `--tf-path`, `PCT_TFPATH`, `TERRAGRUNT_TFPATH`, and picking between the two tools - that must be consulted *even when no version was requested*, which is why this dispatch is unconditional rather than only firing when `$version` is non-empty); otherwise, given an empty `$version` it checks whether `$tool` is actually on `$PATH` - if so, returns the bare `$tool` name unchanged (skip resolution, exactly as before this feature existed), and if not, exits with an actionable error (naming the tool and the hook, via `$HOOK_ID`, and suggesting `--hook-config=--tool-version=<version>`) rather than deferring to whatever generic "command not found" failure the hook's own later invocation would have produced; otherwise it runs the generic download-and-cache logic itself, in its own body, to actually resolve the pin.
   *Avoiding recursion, without a second function or a guard parameter*: `common::get_tf_binary_path`, once it decides the concrete tool ("terraform" or "opentofu" based on `$PATH` availability), calls back into `common::resolve_tool_path` with that concrete name to do the actual pin-and-cache step - reusing the same generic logic every other tool uses, per Decision 1. Two earlier attempts at this recursion problem were rejected in turn: (a) a separate `common::resolve_tool_path_` function that `common::get_tf_binary_path` called directly, bypassing the dispatch entirely - reverted, since the whole point was one function; (b) an internal-use-only third argument (`skip_tf_dispatch`) that `common::get_tf_binary_path`'s callback set to skip the dispatch branch on its way back in - worked, but is an implicit, easy-to-forget flag on an otherwise 2-argument function. The dispatch sentinel is `"tf"` specifically (not `"terraform"`) *because* it can never collide with the concrete decided value: `common::get_tf_binary_path`'s callback always passes the literal string `"terraform"` or `"opentofu"`, never `"tf"`, so `[[ $tool == tf ]]` is naturally false on that second call and it falls straight through to the generic logic - no flag, no second function, no possibility of forgetting to pass a guard. `"tf"` was chosen to match the naming already established elsewhere in this codebase for the same Terraform-or-OpenTofu concept (`--tf-path`, `tf_path`, `common::get_tf_binary_path`).
   *Earlier, incorrect version of the dispatch itself*: pushing the "skip resolution if no version requested" check into each *caller* (a `[[ $tool_version ]] && common::resolve_tool_path ... || echo "$tool_name"` ternary) instead of into `common::resolve_tool_path` itself. This looked equivalent for ordinary tools, but was a real bug for Terraform/OpenTofu specifically: it caused `--tf-path`/`PCT_TFPATH`/`TERRAGRUNT_TFPATH` to be skipped entirely whenever no `--tool-version` was set, since the caller's ternary never even called into the resolver (and thus never reached `common::get_tf_binary_path`) in that case. Caught by an end-to-end test of `--tf-path` with no version pin set.
   *Consequence worth calling out*: the download-failure-aborts-rather-than-falls-back property (the generic logic fails via `exit 1`, not `return 1`) still holds with this design - callers now do a plain `tool_path=$(common::resolve_tool_path "$tool_name" "$tool_version")` with no `||` fallback of their own at all, so a failed pinned download unwinds the whole `$(...)` and aborts the calling hook script directly. Verified directly.

10. **`common::per_dir_hook` threads the resolved `tool_path` (not `tool_name`) through to both `per_dir_hook_unique_part` and `run_hook_on_whole_repo`** (the latter previously received no tool-related information at all - not even the old, unused `$tf_path`) - hooks' own callback functions never need to know whether they're being resolved via the generic path or the Terraform-specific one.

11. **Scope: only tools already shaped like `common::install_from_gh_release`'s GitHub-release-binary model** (tflint, terraform-docs, tfsec, trivy, terrascan, infracost, tfupdate, hcledit, terragrunt), plus the bespoke terraform/opentofu path (HashiCorp Releases API, same shape, already special-cased in `common::get_tf_binary_path`). `checkov` (pip) is explicitly excluded — forcing it through a GitHub-release-shaped path would fight its actual, already-working distribution model for no benefit. Represented by an empty `tool_name` (Decision 8), which `common::resolve_tool_path` (Decision 9) short-circuits to a no-op.

12. **Renovate bumpability ships as documentation, not code.** Renovate's built-in `pre-commit` manager only understands `repo:`/`rev:` and `additional_dependencies` for exactly three languages (go/node/python); it has no visibility into `args:`/hook-config strings and structurally never will via that manager. Only a `customManagers` (regex) entry can see inside an `args:` string, and by construction that config lives in the *consumer's* `renovate.json5`, not this repo's. The deliverable is therefore a copy-paste recipe in `README.md`, using the `# renovate: datasource=... depName=...` annotation convention already established (if, in the one reference example checked, not actually wired up) for Dockerfile `ARG *_VERSION` pins elsewhere in this ecosystem.

13. **No `Dockerfile` / `.dockerignore` changes.** `tools/install/*.sh` is already allow-listed and git-tracked, so it already arrives at hook run-time via pre-commit's own repo-clone step in both bare-metal and Docker usage. A defensive, redundant copy into the final Docker stage was considered and rejected as non-load-bearing: any environment unable to reach GitHub to clone the *hooks repo* itself already can't run pre-commit-terraform at all, independent of this change.

14. **`--tf-path` doubles as an explicit terraform/opentofu selector when combined with `--tool-version`, instead of always being read as a literal binary path.** `common::get_tf_binary_path` checks `--tf-path` first (highest precedence, as always) - but only treats it as a literal path and returns early when `--tool-version` is *not* also set. When `--tool-version` *is* also set, `--tf-path`'s value (if any) is instead matched against `terraform` / `opentofu`|`tofu` to pick which of the two to pin explicitly (falling through to the existing `$PATH`-based auto-detection from Decision 8/9 when `--tf-path` isn't set at all), or rejected with an error for any other value - a literal custom binary path and a version pin can't both apply to the same invocation, so erroring is preferable to silently picking one over the other. This is what lets a user force pinning OpenTofu even on a machine where `terraform` also happens to be on `$PATH` (which the plain auto-detection would otherwise always prefer).
    *Regression caught while implementing this*: an intermediate version nested the entire `--tool-version` check *inside* the `if [[ $hook_config_tf_path ]]` branch, meaning `--tool-version` alone (the overwhelmingly common case, with no `--tf-path` set at all) silently stopped being consulted at all - the `elif` chain fell straight through to `PCT_TFPATH`/`TERRAGRUNT_TFPATH`/plain `$PATH` lookup instead, with no error and no indication anything was wrong. Caught by an end-to-end test resolving `--tool-version` with no `--tf-path` set. Fixed by restructuring the precedence chain so the literal-path return only happens when `-z $tool_version`, and the `--tool-version` branch is its own top-level `elif` (reachable with or without `--tf-path` set), matching how Decision 9 already documents this same "must be consulted even when combined with other settings" requirement for the Terraform-specific rungs in general.

## Risks / Trade-offs

- **[Risk]** No checksum/signature verification of downloaded binaries. → **[Mitigation]** Matches existing build-time mechanism and the reference script's own precedent; not a regression. Natural, separable follow-up.
- **[Risk]** Cache directory grows unbounded (every version ever requested persists indefinitely). → **[Mitigation]** Out of scope for v1; document that the cache dir is safe to delete manually. A GC command is a plausible later addition.
- **[Risk]** A Docker container's filesystem is ephemeral per `docker run`; without a mounted volume, every fresh container re-downloads. → **[Mitigation]** Document mounting the cache dir, exactly as `TF_PLUGIN_CACHE_DIR` is already documented today — same shape as an existing, already-accepted trade-off, not a new class of problem.
- **[Risk]** GitHub API rate limiting on the *runtime* download path (distinct from the already-solved build-time path from [#946](https://github.com/antonbabenko/pre-commit-terraform/issues/946)). → **[Mitigation]** The invoked installer script already has `GITHUB_TOKEN`-aware curl-header logic; it applies automatically at run-time too, since we invoke the same script. Document exporting `GITHUB_TOKEN` for users who hit limits.
- **[Risk]** Spawning a full `bash tools/install/<tool>.sh` subprocess has more overhead than an inline function call. → **[Mitigation]** Only happens on a cache miss (first time a given version is requested on a given machine); amortized to near-zero after that, and negligible next to the network download itself.
- **[Trade-off]** Invoking `tools/install/<tool>.sh` at hook run-time gives these scripts two audiences/call sites (Docker build `ARG`-driven, and hook-config-version-driven) instead of one. The one behavior change required of them (conditional `/.env` sourcing) is small and backward-compatible, but future contributors adding a new tool need to know both call sites exist. → **[Mitigation]** Update `CONTRIBUTING.md`'s existing "Add new hook" checklist accordingly.
- **[Trade-off]** Maintainer sentiment on the broader "automate dependencies" question is genuinely mixed. This design deliberately stays narrow (opt-in, bash-only, reuses existing code by invocation rather than reinvention, zero effect when unused) to be an easier "yes" than the general auto-installer idea the thread has circled without resolving — but similar reviewer pushback should still be expected and isn't fully preventable by scoping alone.

## Migration Plan

- Purely additive/opt-in: no existing `.pre-commit-config.yaml` requires any change, and no default behavior changes for hooks that don't set `--tool-version`.
- Rollback is a plain revert of the `hooks/_common.sh` addition, the one `tools/install/_common.sh` conditional-sourcing line, and the per-hook call sites; nothing else in the system depends on the new code path existing.
- No data migration; the cache directory is created lazily on first use.
